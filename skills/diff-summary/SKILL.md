# diff-summary（変更差分サマリ）

実装・変更作業の結果を、人間のレビュアーが「全行を読まずに監査できる」形にまとめるためのスキル。
git の diff は既に存在する。この報告の価値は差分の再掲ではなく、**何を成立させたか（意図）・どこを信用してよく、どこを信用してはいけないか**を正直に伝えることにある。

出力はチャットに Markdown でそのまま書く。ファイルには保存しない。

## 進め方

### 1. 実態を把握する（記憶だけに頼らない）

報告を書く前に、実際の状態を確認する。記憶ベースで書くと、やっていない検証を「やった」と書いてしまう事故が起きる。

- `git diff --stat` と必要なら `git diff` で、実際に何が変わったかを確認する。
- このセッションで**実際に実行した**検証コマンド（ユニットテスト、E2E、`npm run check` など）と、その結果を正確に思い出す。実行していないものを「テストでカバーした範囲」に書かない。
- 元の spec / 依頼の**目的**を確認する。件名はここから書く。

### 2. 下記テンプレートに沿って出力する

以下の構成・見出しを**そのまま**使う。

```markdown
<件名: spec の目的を 1 行で（命令形・簡潔に）>

## 何を変えたか

## 設計判断と却下した代替案

## テストでカバーした範囲

## テストでカバーしていない範囲

## 自信のない箇所・懸念
```

### 3. 正直性セクションを最後に必ず見直す

出力直前に「テストでカバーしていない範囲」と「自信のない箇所・懸念」をもう一度読む。
ここが薄い／空だと報告全体の信頼が崩れる。一度疑って、書き出せていない前提がないか確認する。

## 各セクションの書き方

### 件名

- 1 行・命令形・簡潔。
- 「やったこと」ではなく spec の**目的**を書く。実装手段ではなく、成立させたい振る舞いを書く。
- ❌ `validateToken 関数を追加` （手段の説明）
- ⭕ `期限切れトークンでのアクセスを 401 で拒否する` （目的・振る舞い）

### 何を変えたか ← このフォーマットの中核

**意図ベースで書く。差分の説明ではない。**
「どのファイルをどう触ったか」ではなく「何を成立させたか／どんな振る舞いになったか」を書く。
ファイル名・関数名の列挙に逃げると、git log を読むのと変わらず報告の意味がなくなる。可能なら Before / After で振る舞いの変化を書く。

- ❌ 差分ベース: `auth.ts に validateToken を追加し、middleware.ts から呼ぶようにした`
- ⭕ 意図ベース: `これまで期限切れトークンでも API を通過できていたのを、期限切れなら 401 を返すようにした。フロントは 401 を受けて再ログインへ誘導する`

### 設計判断と却下した代替案

- 採用した方針と、検討して見送った代替案・その理由を書く。
- spec で確定済みの方針も、実装中に選んだ非自明な判断も両方含める。レビュアーが「なぜこの選択になったか」を後から追えるようにする。
- 代替案を無理に捏造しない。本当に一択だった些末な変更なら「自明なため代替案の検討なし」と書く。

### テストでカバーした範囲

- **観点で書く。**「テストを書いた」ではなく「何を確認できたか」を書く。
- 自動検証（ユニット / E2E / `npm run check` など）と、手動の振る舞い検証を区別する。
- **実際に実行したものだけ**を書く。実行していない検証をここに書くと監査が崩れる。
- ⭕ 例: `ユニットで期限切れ・有効・不正形式の 3 トークンが期待どおり分岐することを確認。npm run check は green`

### テストでカバーしていない範囲 ← 重要・正直に

- 検証していない経路・条件・前提。手動確認に留めた点。
- 「無い」と思っても一度疑って書き出す。**空欄にしない。**
- レビュアーがどこに目を向けるべきかを示すのがこのセクションの役割。ここを薄くすると報告全体が信用されなくなる。
- ⭕ 例: `同時リフレッシュ時の競合は未検証。本番相当の負荷・実 KV での挙動は未確認。エラー文言の i18n は手動で 1 言語のみ目視`

### 自信のない箇所・懸念 ← 重要・正直に

- 判定に揺らぎがあった点、未解消のリスク、将来壊れそうな箇所。
- **無ければ「なし」と明記する**（書き忘れと区別するため空欄にしない）。
- ⭕ 例: `トークン検証のタイムゾーン依存に確信が持てない。サーバとクライアントの時計ずれ次第で境界ケースが揺れる可能性`

## アンチパターン（やってはいけない）

- 「何を変えたか」が差分のダンプになっている（ファイル名・関数名の列挙）。
- 「テストでカバーした範囲」に、実際には実行していない検証を書く。
- 「カバーしていない範囲」「懸念」を空欄にする、または当たり障りのない一般論で埋める。
- 件名が手段の説明になっている（目的になっていない）。
- カバーした範囲とカバーしていない範囲が混ざっている（境界を曖昧にしない）。
