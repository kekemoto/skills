description: Elicit requirements for a big or vague development goal — interview the user about genuine ambiguities via AskUserQuestion, decompose into a 1-PR-per-unit roadmap, and write a spec file for each PR into specs/<project-slug>/. Specialises in requirement elicitation → spec files; does NOT implement. Usually invoked by the /harness orchestrator, but can be run standalone. Invoke explicitly only.

大きく曖昧な開発目的を 1 つ受け取り、**ヒアリングで要件を引き出し → 1 PR 単位への分解 → 各 PR の spec ファイル化**までを担う要件定義スキル。
通常は `/harness` オーケストレータが状態を見て呼び出す。`/harness-hearing <目的>` で直接起動してもよい。
**spec 群を作り終えた時点で停止する**。実装は `/harness-coder` の責務で、**呼び出し経路に関わらず、spec 群を提示したらこのスキルは停止する**（ユーザーが spec をレビューしてから実装を明示指示する運用）。

## project と並列性

1 つの「目的」= 1 つの **project** = 1 つの `specs/<project-slug>/` ディレクトリ = 1 本の `feature/<project-slug>` ブランチ = 1 本の main 向け PR。複数 project を**並列に**抱えてよい（例: `specs/play/` と `specs/auth-overhaul/` が同時に in-flight）。このスキルは **常に 1 つの project に対して spec 群を作成**する。既存 project に spec を足したいケースは対象外（その場合は `/harness-spec` を使う）。

project slug は kebab-case（後段の harness-coder が `feature/<slug>` ブランチ名にそのまま使う）。引数で渡されたら尊重し、なければ目的から仮命名して**保存前にユーザー確認**を取る。

## このスキルの責務範囲

- 含む: 目的の解釈 / ヒアリング / 実装計画（1 PR 分解）/ 各 PR の spec 作成
- 含まない: 受け入れ条件の精査 / 実装 / 検証 / 実行順制御・統合 → すべて `/harness-coder`
- 含まない: どの段階を実行すべきかの判断・段階間の制御 → `/harness` オーケストレータ

「1 PR 1 責務で収まる」ことが最初から明らかな小さな目的なら、ヒアリングを挟まず `/harness-spec` で spec を 1 本作る方が早い（`/harness` はこの振り分けも自動で行う）。

入力はユーザーの粗い目的記述、出力は `specs/<project-slug>/<NN>-<unit-slug>.md` × N（1 PR = 1 spec、`<NN>` は **project 内**の実装順を表す 2 桁通し番号）。

## 基本原則

- 人間確認はデフォルトではなく例外。**迷ったらエスカレーション**（判定基準: `../harness/risk-criteria.md`）
- ヒアリングは網羅ではない。**ask か assume かは「曖昧さがあるか」ではなく「その仮定を外したときの手戻りコスト」で決める**（下記「ask / assume / escalate の判定」）
- 「PR を細かく刻むこと」と「PR の境界を意味で揃えること」の両立を優先する
- spec は実装手順ではなく、成立条件を記述する

## ask / assume / escalate の判定

洗い出した各曖昧さを、**AI が合理的な推定を作れるか**ではなく、**その推定が外れたとき手戻りがどこまで広がるか**で振り分ける。これが hearing の中心的な判断軸。

| 手戻りの広がり | 例 | 扱い |
| --- | --- | --- |
| **局所** — 1 spec 内で直せる／後から安く変えられる | 画面文言、内部命名、実装手法の細部、UI レイアウト、エラーメッセージ表現 | **assume**。仮定として明示し前進。質問にしない |
| **横断** — 複数 spec の再分解・再実装に波及／後から変えにくい構造 | データ形状・DB スキーマ、公開 API シグネチャ、モジュール境界の置き方、PR 分割の前提そのもの、認証・セッションの方式 | **ask**。`AskUserQuestion` で確定してから進む |
| **リスクゾーン該当** | 認証・認可・権限、課金、個人情報・機密、削除・不可逆、公開契約変更、DB スキーマ変更 | **escalate**。仮定で処理せず即時ユーザーに上げる（判定基準: `../harness/risk-criteria.md`） |

判定の指針:

- **「合理的な推定が作れる」ことは assume の十分条件ではない**。推定できても、外すと横断的に高くつくなら ask に倒す
- 逆に、複数の妥当な解釈が併存していても、**どれを選んでも 1 spec 内で安く直せる**なら ask せず assume する（網羅的アンケートを避ける）
- 「横断」と「リスクゾーン該当」は重なることが多い。重なったら escalate（上位）を採る
- **迷ったら上位（assume → ask → escalate）に倒す**
- 横断かどうかの判断材料は、ステップ 4 の PR 分解と表裏一体。「この仮定が外れたら PR の切り方自体が変わるか？」を自問する

## 自律確定した仮定の報告

**ユーザーへの報告・spec 群提示のタイミングで、自律確定した非自明な仮定を列挙する**。

- 対象は「複数の妥当な解釈がありえたが assume したもの」「明示されていない前提を補ったもの」。slug 命名や自明な判断はいちいち挙げなくてよい
- 横断的な曖昧さは ask に回っているはずなので、ここで残るのは原則「局所」と判断して assume したもの。それでも後で覆ると影響が出る仮定は、何をなぜ仮定したかを一言添える。spec に関わるものは当該 spec の「仮定 / 不確実性」セクションにも記録する
- リスクゾーン該当の論点は仮定として処理せず、即時ユーザーに上げる（判定基準: `../harness/risk-criteria.md`）

## ステップ駆動

各ステップ終了時に簡潔にユーザー報告する。

### 1. 目的の整理

- ユーザー提示の目的を言い換え、背景・前提・制約を整理する
- 粗い入力で OK。不足は AI が推定で埋める
- 完成済み仕様を人間が事前に用意することを前提にしない

### 2. 仕様提案・ヒアリング

- 目的を機能要求と非機能要求に整理する
- 想定ユースケース・既存システムへの影響を推定する
- **曖昧さを洗い出し、「ask / assume / escalate の判定」で振り分ける**。これがこのステップの肝
  - **assume**（局所） → 仮定付きで前進。質問にしない。後段で spec の「仮定 / 不確実性」に反映する
  - **ask**（横断） → 下記の作法で `AskUserQuestion`
  - **escalate**（リスクゾーン該当） → 仮定にせず即時ユーザーに上げる（ステップ 3 でも改めて全体判定する。判定基準: `../harness/risk-criteria.md`）
- 振り分けの基準と落とし穴は上の「ask / assume / escalate の判定」が正本。特に各曖昧さに「これが外れたら PR の切り方が変わるか？」を一度当て、変わるなら横断＝ask に倒す
- `AskUserQuestion` の作法:
  - 1 回あたり 1〜4 問、必要に応じて複数回繰り返す
  - 各質問は header（短いラベル）と description（選択時の意味）を明確に
  - 推奨案がある場合は先頭に置き label に `(Recommended)` を付ける
  - 「Other」選択肢は自動で付与されるので手動追加しない
- ヒアリング結果（ask の回答も、assume した仮定も）は後段で spec の「仮定 / 不確実性」セクションに反映する

### 3. 確認要否判定

- 仕様提案・ヒアリング結果を `../harness/risk-criteria.md` のゾーン定義に照らして判定する
- 🔴 Danger / 「ゾーンに依らず止める論点」に該当するなら、論点・影響範囲・選択肢・推奨案を提示しユーザー判断を待つ
- 🟡 Caution / 🟢 Free なら次へ（Caution は後段の spec で「設計判断・影響範囲・自信のない箇所」として記録対象になる旨を控えておく）
- 中心は「不明点があるか」ではなく「AI が自律的に確定してよい種類の論点か」。ステップ 2 で解消済みの論点は再掲しない

Danger に当たる論点の一覧は `../harness/risk-criteria.md` が正本。ここで再掲しない。仕様解釈が複数併存する場合も「ゾーンに依らず止める論点」として同様に上げる。

### 4. 実装計画（1 PR 単位への分解）

目的を **1 統合単位 = 1 PR = 1 検証可能単位** まで分解する。

- 統合単位とは、変更を独立に検証し、統合可否を判断できる最小単位
- 自動変換・整理目的の変更と機能変更は分離する
- モジュール境界（user / stories / play など、`CLAUDE.md` 参照）をまたぐ変更は別単位に切る
- 各 PR は: 目的・スコープ・受け入れ条件・検証方針・切り戻し を持つ
- 依存関係を整理し、実装順序を設計する（順序はファイル名番号 `<NN>` で表現する。先行する単位ほど小さい番号）
- 各 PR の unit slug（kebab-case）を仮命名する
- **project slug を確定する**: 引数で渡されていればそれを使う。無ければ目的全体を表す kebab-case の slug を仮命名する。既存の `specs/<slug>/` と衝突しないことを確認する（衝突するなら別名を提案）
- **ロードマップ全体（project slug + 1 PR ずつのリスト + 推奨実装順）をユーザーに提示し承認を得る**
  - 「PR が多すぎる / 細かすぎる / 大きすぎる / 順序が違う / project slug を変えたい」等のフィードバックがあれば再分解・再命名する

### 5. spec 群の作成

承認された各 PR について `/harness-spec` を呼んで `specs/<project-slug>/<NN>-<unit-slug>.md` を作成する（呼び出し時は `<project-slug>/<NN>-<unit-slug>` の形で指定し、ステップ 4 で確定した project と番号をそのまま渡す）。

- **デフォルトは一括作成**。ロードマップ承認後、全 spec をまとめて作る（中間報告は省略してよい）
- 例外: spec 作成中に **新たな曖昧さ**や **エスカレーション基準該当**が見つかったら、その時点で一旦止めてユーザー判断を仰ぐ。解消後に残りを続行する
- ステップ 2 のヒアリング結果と仮定は、関連する spec の「仮定 / 不確実性」セクションに反映させる
- 新規作成時の `status` は必ず `pending`
- ファイル名の番号 `<NN>` はステップ 4 で決めた実装順（= 依存関係順）どおりに採番する。採番ルールの詳細は `/harness-spec` が正本。ここでは「ロードマップの順に連番を振り、依存先が必ず小さい番号になるようにする」だけ押さえる。番号は **project 内でユニーク**であればよく、他 project の番号と揃える必要はない
- spec は「どう実装するか」ではなく、「何が成り立てばその単位が完了とみなせるか」を定義する

### 仕上げ: spec 群の提示・停止

ステップ 5 完了後、ここで harness-hearing としての作業を閉じる。**project slug と作成した spec 群を一覧で提示する**。冒頭に project slug（= 後段の `feature/<slug>` ブランチ名）を明示し、各行に以下を含める：

- spec ファイルパス（`specs/<project-slug>/<NN>-<unit-slug>.md`）
- 目的の 1 行要旨
- 推奨実装順（番号順）

そのうえで、**呼び出し経路に関わらずここで停止する**。`/harness` 経由でも実装へは自動で進まない（spec レビューゲート）。次の案内を添える：

> specs 群を実装するには、内容をレビューのうえ `/harness-coder`（または入口の `/harness`）を実行してください。
> 実装前に AI レビューで懸念・仮定・不確実性を解消したい場合は `/harness-spec-review` を実行してください。

**このスキル自身は実装に進まない**。実装着手は、ユーザーが spec をレビューしたうえで明示的に指示したときに限る。

**巻き戻し**: 途中で目的そのものの再分解が要ると判明したら、このスキルのステップ 1 からやり直す。

## 連携 skill

- `AskUserQuestion` — ステップ 2（ヒアリング）
- `../harness/risk-criteria.md` — ステップ 3、および任意のステップで論点を感じたときに参照するリスク判定基準
- `/harness-spec` — ステップ 5（spec 群作成）。1 PR で収まる目的なら単体でも使う
- `/harness-coder` — 実装の引き継ぎ先（このスキル自身は呼ばない。ユーザーがレビュー後に明示起動する）
- `/harness` — 入口オーケストレータ。状態を見てこのスキルを呼ぶかどうかを判断する
